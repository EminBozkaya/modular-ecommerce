## ✨ Was diese Plattform besonders macht?

Dieses Projekt ist nicht einfach nur eine weitere E-Commerce-Vorlage; es ist eine **vollständig anpassbare White-Label-Plattform**, die entwickelt wurde, um maximale UI/UX-Flexibilität direkt über das Admin-Panel zu bieten.

* **Vollständige Design-Kontrolle:** Administratoren können das visuelle Erscheinungsbild nahtlos ändern, ohne in den Code eingreifen zu müssen. Sie können im Handumdrehen Logos austauschen, die globale Farbpalette aktualisieren und Schriftarten anpassen, um sie perfekt an jede Markenidentität anzugleichen.
* **Flexible Layouts:** Die Schaufenster-Menüs (Storefront-Menüs) können völlig frei neu angeordnet werden. Die Header- und Footer-Bereiche sind stark konfigurierbar, und Werbe-Banner können nach Belieben zwischen scrollenden Laufschriften oder festen statischen Blöcken umgeschaltet werden.
* **Schaufenster-Anpassung:** Die Startseite und das Schaufenster sind hundertprozentig modular aufgebaut. Bereiche wie Hauptkategorien, Kundenbewertungen und Newsletter-Blöcke lassen sich dynamisch aktivieren, deaktivieren oder lückenlos anpassen.
* **Umfassende Mehrsprachigkeit (7 Sprachen):** Jede einzelne der oben genannten Design-Anpassungen sowie sämtliche Produkt- und Kategoriedaten funktionieren dynamisch über 7 integrierte Sprachen hinweg. Wann immer ein neues Produkt oder eine Kategorie hinzugefügt wird, können Administratoren mühelos Übersetzungen für jede dieser 7 Sprachen direkt im Admin-Panel hinterlegen und so ein nahtloses, lokales Einkaufserlebnis für ein globales Publikum sicherstellen.

## Architektur

Ein "Modularer Monolith" (Modular Monolith) mit einer strikten Schichtentrennung (Clean Architecture), CQRS durch MediatR, und einem vollständig umgesetzten Domain-Driven Design (DDD). Abhängigkeits-Regeln zwischen den einzelnen Layern werden strikt zur Compile-Zeit über `NetArchTest.Rules` validiert und erzwungen.

### Sprachunabhängiges Multi-Sprachen-Design

Erfassungs- bzw. Anzeigennamen für Produkte und Kategorien werden nicht direkt am Produkt gespeichert, sondern in dedizierten Übersetzungstabellen (`ProductTranslations`, `CategoryTranslations`), referenziert durch den zusammengesetzten Schlüssel `(EntityId, LanguageCode)`. Dadurch wird vermieden, dass eine spezifische Sprache "fest" vorgegeben ist – stattdessen ist jede Sprache auf demselben Status.

Die in der Datei `appsettings.json` definierte Variable `DefaultLanguage` regelt, welche Sprache das System als "Fallback" heranzieht, falls eine angeforderte Sprachversion eines Textes fehlt. Eine Instanz in Deutschland konfiguriert folglich vorab `DefaultLanguage: "de"`, woraufhin Administratoren initial deutschen Content einpflegen können. Englische oder türkische Inhalte werden später flexibel im Editor ergänzt.

Dieser Ansatz macht die Applikation konzeptionell zu einer echten, global skalierbaren White-Label-Lösung, für deren Lokalisierung keinerlei Codeanfassungen nötig sind.

### Abgegrenzte Kontexte (Bounded Contexts)

| Kontext | Domänen-Entitäten | Kern-Invarianten |
|---------|-------------------|------------------|
| **Katalog** | Product, Category, Unit | Preis (Money) ist unveränderlich & >0, Stückzahl (StockQuantity) >= 0, Eltern-/Kind-Hierarchie |
| **Warenkorb** | Basket, BasketItem | Preiskopierung beim Hinzufügen, Gast- (Session-ID) und Kundenbezug (User-ID), Dezimalmengen verwalten (für kiloweise Verkäufe) |
| **Bestellung** | Order, OrderItem | Status-Maschine: (Ausstehend &rarr; Bezahlt &rarr; In Bearbeitung &rarr; Versendet &rarr; Zugestellt / Storniert) |
| **Zahlung** | PaymentRecord | Verhindern von Doppelzahlungen (Idempotenz) durch (OrderId, IdempotencyKey)-Indizierung |
| **Identität** | AppUser | PBKDF2 Hashing, JWT via httpOnly Cookie, obligatorische Refresh Token-Rotation |
| **Wunschzettel** | WishlistItem | Eindeutige Kombination pro Benutzer und Produkt |

### Abhängigkeitsfluss

```text
Domain         <- (völlig unabhängig -- KEINE Fremdreferenzen)
Application    <- Domain
Persistence    <- Domain (ausschließlich)
Infrastructure <- Domain, Application
API            <- Application, Persistence, Infrastructure
```

> Die Persistenzschicht (Persistence) ist explizit nur von der Domäne (Domain) abhängig – nicht von der Applikation. Dadurch wird Inversion of Control gewährleistet. Repositories werden im Domain-Layer deklariert, in der Persistence jedoch physisch angewandt.

## 🚀 Einrichtung & Start

Wir bieten zwei direkte, unkomplizierte Wege, um das Projekt zum Laufen zu bringen. Wenn Sie einfach die Oberfläche, die Design-Anpassungen, sowie den User-Flow auf einen Blick begutachten wollen (z. B. optimal für Portfolio-Präsentationen), können Sie den **Mock Data Ansatz** heranziehen. Wenn Sie jedoch die vollkommene Backend-Technologie bewerten und durchtesten möchten, greifen Sie zur **Full Stack Version**.

### Voraussetzungen

| Werkzeug | Version | Erforderlich für |
|----------|---------|------------------|
| [Node.js](https://nodejs.org/) | 18+ | Frontend & Mock Data zwingend erforderlich |
| [.NET SDK](https://dotnet.microsoft.com/download) | 10.0+ | Vollversion (Full Stack) zwingend erforderlich |
| [Docker](https://www.docker.com/) | Neueste | Dringende Empfehlung zur schnellen Serverintegration |

### Option 1: Schneller Start mittels "Mock Data" ⚡
Dieser Modus betreibt **ausschließlich die React SPA (Frontend) Umgebung**. Das gesamte Backend wird virtuell vom Frontend zur Verfügung gestellt (gemockt). Dies ermöglicht es Ihnen, Katalog-Suchvorgänge, die Warenkorb-Engine, Layout-Wechsel und den fließenden Umgang mit 7 verschiedenen Sprachen in Echtzeit durchzuführen, ohne Server-Dienste starten zu müssen.

```bash
# 1. Starten Sie mit dem Klonen des Kern-Repository
git clone <repo-url>
cd ECommerce/src/ECommerce.Web

# 2. Lade alle Javascript-Bibliotheken herunter
npm install

# 3. Kontrollieren Sie den Environment-Pfad in .env.development.local
# Stellen Sie zwingend sicher, dass Folgendes festgelegt ist:
# VITE_USE_MOCK_API=true

# 4. Los geht's
npm run dev
```

*Das war's bereits!* Öffnen Sie in Ihrem Browser den von Vite angegebenen Localhost-Link und begutachten Sie das funktionierende E-Commerce-Zentrum unmittelbar.

---

### Option 2: Full-Stack Start (Live-Datenbank & Redis) 🏗️
Entscheiden Sie sich für diesen Ablauf, um die tatsächliche .NET 10 API mitsamt der aktiven PostgreSQL- und Redis-Verbindungen hochzufahren und das Frontend zielgerichtet an dieses System zu knüpfen.

#### Schritt A: Infrastrukturen starten (via Docker)
Lassen Sie uns PostgreSQL und Redis schnell über den Docker Hub beziehen:
```bash
# PostgreSQL Container aktivieren
docker run -d --name ecommerce-db -e POSTGRES_USER=postgresUser -e POSTGRES_PASSWORD=postgresPassword -e POSTGRES_DB=ECommerceDb -p 5432:5432 postgres:16-alpine

# Redis Container aktivieren
docker run -d --name ecommerce-redis -p 6379:6379 redis:7-alpine
```

#### Schritt B: Starten der .NET API Basis
```bash
# Stellen Sie sicher, dass sie sich im Projektwurzelverzeichnis befinden
cd ECommerce

# Binden Sie die EF Core Migrationen an.
dotnet ef database update --project src/ECommerce.Persistence --startup-project src/ECommerce.API

# Setzen Sie die Logik unter Spannung
dotnet run --project src/ECommerce.API
```
*Ihre API ist nachfolgend einwandfrei einsatzfähig und kann zudem über Swagger via `https://localhost:5001/swagger` beobachtet werden.*

#### Schritt C: Starten des Frontends
Nutzen Sie ab hierbei ein weiteres Terminal-Fenster:
```bash
cd ECommerce/src/ECommerce.Web

# Fehlen die Module noch? Dann rasch ausführen:
npm install

# Ändern oder belegen Sie die Environmentvariablen (.env.development.local), 
# um das Frontend mit dem lebendigen Backend interagieren zu lassen:
# VITE_USE_MOCK_API=false
# VITE_API_BASE_URL=https://localhost:5001

# Aktivieren
npm run dev
```

*🎉 Glückwunsch! Das Modular Monolith System läuft in seinem vollem Glanz!*

## Sicherheit

| System | Logik (Implementation) |
|---------|----------------|
| Zugangsberechtigung | JWT-Handling erfolgt unsichtbar über **httpOnly secure cookies** (Vollkommener Verzicht auf localStorage) |
| Token Rotation | Wir greifen auf Refresh-Tokens mit **striktem Rotaus-Verfahren** bei jedem Neuziehen zu |
| Token Lebensdauer | Access Tokens existieren maximal 15 Minuten – kein Erlauben von Systemzeitverzögerungen (Clock Skew) |
| Hash-Logarithmen | Wir verbürgen uns für PBKDF2 (SHA-256) und nutzen gewaltige (100K iterierte) Kodierungen |
| Zahlungsstrukturicherheit | **Ausschließlich Token-Kommunikation** &mdash; Zu keiner Zeit werden echte Debit- bzw. Kreditkartendaten im ECommerce-Archiv protokolliert |
| Vorbeugung von Parallel-Berechnungen| Verknüpfter Systemindex `(OrderId, IdempotencyKey)` filtert doppelklickende unbedachte Doppelbezahlungen restlos ab |
| Durchsatzeingrenzungen | Maximal 100 Systemanfragen je IP in der Minute (FixedWindowLimiter Abwehrmechanismus) |
| CORS Erlaubnisse | Hart implementierter **Whitelist-Mauerfilter**, um Zugangslecks von fremddiensten abzufangen |
| Datenentsorgung | Wir bedienen uns eines Soft-Deletes. In der Praxis geht deshalb **weder Buchungszeile noch Information je verloren** |
| Optischer Frontendschutz | Unser Frontend baut Wände nur bezüglich optimaler Benutzer-Routensteuerung (UX); **Härteentscheidungen trifft das sichere C# Backend stets alleinig** |
| Backend Torhüter | Wir kontrollieren sensible Backend-Hintereingänge knallhart via `[Authorize(Roles = "Admin")]` Signatur |
